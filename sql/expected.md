# Результаты на синтетических данных

Q1: (1, OPEN), (4, OPEN).
Q2: 1, 5.
Q3: (1, FileQueue), (4, MailGateway), (5, AdminConsole).
Q4: (FileQueue, 2), (MailGateway, 1), (AdminConsole, 2), (EmptyService, 0).
Q5: (500, 2), (503, 2).
Q6: (P1, 1), (P2, 1), (P3, 1).

Для Q4 фильтр находится в `ON`: продукт без незакрытых обращений сохраняется в результате. `COUNT(i.id)` считает только найденные обращения; `COUNT(*)` ошибочно дал бы единицу для продукта без совпадений.

`EmptyService` не имеет обращений. Дополнительный тест создаёт `ClosedOnly` с единственным закрытым обращением: оба продукта должны иметь нулевой счётчик. Тесты выполняют запросы из `diagnostics.sql`, а не отдельные копии SQL. Для Q1–Q6 сравниваются все строки, значения и порядок с ожидаемыми результатами выше; дополнительно проверяются два граничных случая Q4.

Для Q5 отдельный тест добавляет одиночную ошибку 502 и второе обращение с 404. Ожидаемые группы остаются `(500, 2)` и `(503, 2)`: `WHERE` исключает клиентские ошибки до группировки, `HAVING COUNT(*) > 1` исключает одиночные серверные ошибки после неё. Дополнительные строки существуют только в изолированной базе теста.

Для Q2 отдельный тест добавляет закрытое обращение без ответственного, незакрытое IN_PROGRESS без ответственного и OPEN с ответственным. В результат дополнительно попадает только IN_PROGRESS: отсутствие ответственного проверяется через `IS NULL`, а «незакрытое» включает и OPEN, и IN_PROGRESS. Изменения данных изолированы в базе теста.

Запуск из корня проекта, Python 3 и стандартная библиотека:

```bash
python3 -m unittest discover -s sql -p 'test_*.py' -v
python3 sql/run.py
```

Я использую синтетические данные для этого учебного расширения.
